## Bootstrap sem dependências prévias

Baixar `bootstrap-dev.sh` ou `bootstrap-dev.ps1` pelo navegador, na branch desta
entrega. Conferir o commit publicado no PR, conservar o arquivo local e rodá-lo
conforme [CONTINUAR_AQUI](../../CONTINUAR_AQUI.md). Não executar um caminho antigo
do host, nem restaurar `.desktop`, links ou scripts privados com caminhos fixos.

O launcher instala somente o pré-requisito Git e a toolchain necessária; o dono
de Python/venv/config/MT5 continua sendo `install.sh` ou `scripts/install/windows.ps1`.
`scripts/setup_development.py` orquestra o restante: valida origem/limpeza dos
checkouts, fixa H/Safety, instala `requirements-dev.txt` no mesmo `.venv`, confere
dependências/imports, doctor, testes focados, checker e testes Super ATR, conecta
as bibliotecas vazias pelos métodos existentes e cria desktop/menu pelo mesmo
componente de atalhos. Não baixa o banco nem ativa um robô.

Destinos existentes com origem, commit ou alterações incompatíveis são recusados.
Novos clones usam `core.autocrlf=false` localmente: hashes/pins não podem mudar
por conversão automática de fim de linha no Windows. Não alterar a configuração
Git global ou regravar arquivos de outra árvore para obter o pin esperado.
Nada de `reset --hard`, `git clean`, reinstalar Python global pelo pip ou copiar
venv antigo. Uma segunda chamada reutiliza fontes e ambiente; não faz pull/checkout
destrutivo em árvore com trabalho. Após uma interrupção, conferir `state/setup.json`
e os logs; clone parcial exige inspeção ou outra pasta, não apagamento automático.
Executar um bootstrap por workspace de cada vez.

Estrutura única:

```text
MT5X/
  repos/app/             # clone de referência; .venv/config/database/logs próprios
  repos/hadouken/        # HPR75 no commit declarado
  repos/safety/          # distribuição aceita; não outra cópia do Framework
  worktrees/             # uma branch/tarefa por agente, sem duplicar ambiente
  studies/               # artefatos identificados por estudo, retidos com orçamento
  downloads/             # partes privadas; remover só após restore conferido
  state/                 # recibos e logs do bootstrap, sem credenciais
```

O estado `development_ready` significa que os checks do wrapper passaram.
`environment_only_checks_pending` não é aceite. Falha gera `failed`; não seguir
como se a fase estivesse concluída. A instalação completa no SO novo e Windows
físico continuam verificações do destino, não fatos comprovados no host antigo.
A preparação não executa a suíte ampla, servidor PostgreSQL ou Tester nativo.
O próximo agente deve rodar os checks exigidos pelo seu recorte/CI, preservar
falhas e usar `tester_lease` antes de qualquer teste MT5 próprio.

## Recuperar a base privada sem o SD

O pacote contém um snapshot SQLite consistente, capturado pela API backup com a
origem somente leitura, 48 tabelas no corte; documentos locais posteriores,
as duas notas de pesquisa, configuração anterior e contexto/WIP histórico útil.
Não inclui venv, Wine, caches, binários regeneráveis, exports repetidos, locks,
PIDs, tokens de posse ou sessões OAuth do navegador/Codex/GitHub/Composio.
Não havia `.env` no projeto no corte. Reautenticar; não procurar senhas em logs.
Separadamente, a mesma página preserva os dois documentos originais `ESTUDOS/`
do HADOUKEN e as três capturas privadas do reteste do Laboratório. Esses anexos
não vão ao GitHub e não são aplicados sobre os clones automaticamente.

Na página privada há o manifesto e as partes em texto base64. Elas ficam abaixo
do limite de leitura de fonte do conector, permitindo ao agente recuperar os
bytes por `read_page_reference` sem screenshot ou copiar manualmente o banco.
O manifesto completo relaciona nome original, nome de download da Library,
referência persistente, SHA do texto e do conteúdo decodificado e ordem das partes.

O agente pode ler o manifesto pela ferramenta Pages, ler os anexos por suas
referências e materializar cada `text` como arquivo UTF-8 sem BOM. Um LF final
do executor só é aceito se recuperar exatamente o SHA canônico; outros bytes
são recusados. Para não levar megabytes ao chat, orquestrar leituras e
escrita em arquivos pelo executor, conferindo hash/tamanho. Também é possível
baixar os anexos pela conta autenticada; o verificador aceita os nomes originais
ou os nomes de download registrados. Não usar URL temporária como referência fixa,
inventar IDs de arquivos ou publicar esses conteúdos no GitHub.

Com as partes e o manifesto baixados para `downloads/`, a partir de `repos/app`:

```bash
python scripts/recover_cloud_backup.py \
  --parts-dir ../../downloads \
  --manifest ../../downloads/cloud-manifest.json \
  --output ../../downloads/MT5X-private-development-20261024.zip \
  --extract-to ../../restored-check
```

Usar o Python do `.venv` (`.venv/bin/python` ou `.venv\Scripts\python.exe`) ou
Python3 do sistema: o verificador só usa stdlib. O ZIP de destino não pode existir;
o diretório de extração também precisa ser novo. Todos os hashes/partes são
conferidos antes de publicar o ZIP; paths externos, links e inventário interno
divergente são recusados antes da extração. O helper verifica `quick_check` do
SQLite extraído e não altera configuração/base ativa. Em FAT/exFAT, escolher um
destino no filesystem local que suporte hardlinks para a publicação sem sobrescrita.

Conferir `CONTENTS.json`, as contagens de tabelas e os registros já existentes.
Reabrir primeiro a cópia de ensaio. Preservar resultados negativos, IDs, hashes,
journal, snapshots e revisões; caminhos antigos de artefatos precisam ser
reconfigurados/requalificados. Hash preservado não certifica fonte financeira.

Só então escolher a cópia de trabalho e apontar a configuração pelo fluxo
`bootstrap configure --db-path ...`. Não sobrescrever um banco que já exista.
Migrar preferências da cópia privada seletivamente; nunca carregar o config
antigo sem revisar caminhos, biblioteca, timezone e conta. Reconferir `allow_real=false`.
WIP documental e contexto antigo são consulta, não instruções para aplicar merges.

# Contrato de dados para a UI Analytics (T13.6)

Proposta de interface de dados v1, registrada em 2026-10-15. Este documento prepara a integração; não declara a
T13.6 concluída. A tela no mt5x e o painel MQL5 ainda dependem do publicador/leitor T13.5 e das dependências listadas
no [plano](../PLANO_DE_TRABALHO.md).

## Princípios

- A UI recebe um DTO serializável produzido pela camada Analytics; widgets não consultam tabelas nem recalculam
  métricas diretamente.
- Cada resultado declara se representa operações executadas, um contrafactual sobre um ledger fixo, uma reexecução
  completa da estratégia ou sinais observados em modo sombra.
- Um filtro aplicado a operações existentes é sempre rotulado como contrafactual. Se bloquear uma entrada mudar
  capital, posições ou sinais posteriores, a comparação exige reexecução completa da estratégia.
- Ausência de informação é `null` com estado e motivo; nunca é convertida em zero, valor neutro ou “sem efeito”.
- “Exploratório”, “validado” e “insuficiente” descrevem a evidência. Frescor é um campo separado; dado vencido tem
  estado `STALE` e não é promovido por ter sido válido antes.
- “Validado” exige os critérios OOS definidos pelo produtor e custos completos para a métrica líquida. Não significa
  probabilidade de sucesso futuro nem autorização operacional.

## Envelope v1

O serviço de apresentação deverá retornar um objeto JSON com este formato lógico:

```json
{
  "schema_version": 1,
  "generated_at_utc": "<ISO-8601 UTC>",
  "as_of_utc": "<instante da decisão ou consulta>",
  "scope": {
    "symbol": "<símbolo>",
    "timeframe": "<timeframe>",
    "strategy_id": null,
    "run_id": null
  },
  "comparison": {
    "kind": "FIXED_LEDGER_COUNTERFACTUAL",
    "label": "Contrafactual sobre operações existentes; sem reexecução",
    "state_changes_replayed": false
  },
  "evidence": {
    "state": "EXPLORATORY",
    "reason": "<motivo curto>",
    "freshness": "CURRENT"
  },
  "provenance": {
    "sources": [],
    "period_start_utc": "<ISO-8601 UTC>",
    "period_end_utc": "<ISO-8601 UTC>",
    "dataset_hash": "<sha256 ou null>",
    "source_revision": "<revisão ou null>",
    "available_at_utc": "<ISO-8601 UTC ou null>",
    "valid_until_utc": "<ISO-8601 UTC ou null>"
  },
  "original": {},
  "candidate": {},
  "delta": {},
  "signals": {
    "accepted": null,
    "blocked": null,
    "source": "NOT_RECORDED"
  },
  "stability": {
    "state": "INSUFFICIENT",
    "method": null,
    "folds": null,
    "estimate": null,
    "interval": null
  }
}
```

Valores permitidos:

- `comparison.kind`: `OBSERVED_LEDGER`, `FIXED_LEDGER_COUNTERFACTUAL`, `STRATEGY_RESIMULATION` ou `SHADOW_LOG`.
- `evidence.state`: `EXPLORATORY`, `VALIDATED` ou `INSUFFICIENT`. `evidence.freshness` é `CURRENT`, `STALE` ou
  `UNAVAILABLE`; a UI mostra `STALE`/`UNAVAILABLE` mesmo que uma avaliação histórica tenha sido validada.
- Cada métrica contém `value`, `unit` e `state`. Para indisponibilidade, `value` é `null` e `state` explica
  `NOT_PROVIDED`, `INCOMPLETE_COSTS`, `INSUFFICIENT_SAMPLE` ou `STALE`.

## Métricas

`original` e `candidate` devem oferecer os mesmos campos, com unidade declarada:

- `n_operations`;
- `net_pnl_total`, `net_pnl_mean_per_operation` e `net_pnl_median_per_operation`;
- `max_drawdown_amount` e `max_drawdown_pct`;
- `peak_exposure` (unidade da fonte, por exemplo contratos ou moeda da conta);
- `costs`, com componentes `spread`, `commission`, `slippage`, `swap` e `fees`, cobertura e componentes ausentes.

`net_pnl_*` só é preenchido quando os componentes de custo requeridos estão completos. Caso contrário, esses campos
ficam `null` com estado `INCOMPLETE_COSTS`; custos observados e resultado bruto podem ser apresentados em campos
separados, sem o rótulo líquido. `delta` contém a diferença candidato menos original apenas para métricas disponíveis
nos dois lados.

`signals.accepted` e `signals.blocked` são `null` com `source: "NOT_RECORDED"` quando não existe log de sinais. Não
se infere zero a partir de um ledger de operações. Contagens só são preenchidas para uma fonte que registra também
sinais bloqueados, como o futuro modo sombra T13.7a.

`stability` informa método, partições temporais, estimativa e intervalo. A UI não deve converter intervalo ou
significância em probabilidade de lucro. Sem evidência temporal suficiente, `state` é `INSUFFICIENT` e os limites
ficam nulos.

## Cobertura atual e trabalho pendente

- T13.4 expõe catálogo e avaliações persistidas, incluindo hash do conjunto, tentativas e resultado JSON. O relatório
  registra que esse contrato ainda não carrega revisão nem validade temporal das barras-fonte.
- A Fase 16 já oferece agregação e re-simulação na lente do Laboratório, mas ainda não há um DTO compartilhado que
  declare comparação contrafactual versus reexecução e proveniência nos campos acima.
- T13.7a ainda não fornece contagem de aceitos/bloqueados; a linha não pode ser deduzida do livro de operações.
- T13.5 precisa definir publicação, validade por característica e disponibilidade no Strategy Tester. A Decisão 7
  segue aberta; a proposta concreta de validade por característica, CSV inicial e fixture point-in-time teve pedido de
  confirmação enviado em 2026-10-15. O painel MQL5 também depende de T12.6. Essas partes seguem pendentes; esta
  proposta não as marca como implementadas.

# Contrato de dados para a UI Analytics (T13.6)

Proposta de interface de dados v1, registrada em 2026-10-15. Este documento prepara a integração; não declara a
T13.6 concluída. A tela no mt5x e o painel MQL5 ainda dependem do publicador/leitor T13.5 e das dependências listadas
no [plano](../PLANO_DE_TRABALHO.md).

## Princípios

- A UI recebe um DTO serializável produzido pela camada Analytics; widgets não consultam tabelas nem recalculam
  métricas diretamente.
- Cada resultado declara se representa operações executadas, um contrafactual sobre um ledger fixo, uma reexecução
  completa da estratégia ou sinais observados em modo sombra.
- Um filtro aplicado a operações existentes é sempre rotulado como contrafactual. Se bloquear uma entrada mudar
  capital, posições ou sinais posteriores, a comparação exige reexecução completa da estratégia.
- Ausência de informação é `null` com estado e motivo; nunca é convertida em zero, valor neutro ou “sem efeito”.
- “Exploratório”, “validado” e “insuficiente” descrevem a evidência. Frescor é um campo separado; dado vencido tem
  estado `STALE` e não é promovido por ter sido válido antes.
- “Validado” exige os critérios OOS definidos pelo produtor e custos completos para a métrica líquida. Não significa
  probabilidade de sucesso futuro nem autorização operacional.

## Implementação disponível na branch

O módulo puro-Python [presentation.py](../../mt5_extracao/analytics/presentation.py) já oferece dois pontos de entrada
para a UI:

```python
from mt5_extracao.analytics.presentation import (
    build_filter_comparison_payload,
    build_hypothesis_catalog,
)

comparison = build_filter_comparison_payload(
    original_ledger,
    candidate_ledger,
    evaluation,  # retorno de mt5_extracao.trade_analytics.rules.evaluate(...)
    scope={"symbol": "EURUSD", "timeframe": "M5", "run_id": "run-123"},
    as_of_utc="2026-10-15T15:00:00Z",
    valid_until_utc="2026-10-15T15:05:00Z",  # só quando o produtor tiver essa validade
    pnl_basis="gross",  # exige também os cinco componentes de custo completos
    pnl_unit="account_currency",
    initial_equity=10000,
)

hypotheses = build_hypothesis_catalog(
    db, pattern_id="breakout-01", symbol="EURUSD", timeframe="M5"
)
```

As duas funções retornam estruturas compatíveis com `json.dumps(..., allow_nan=False)` e não alteram o ledger nem o
banco. O adaptador não importa Tkinter. `as_of_utc`, `generated_at_utc` e `valid_until_utc`, quando informados,
precisam incluir fuso horário; são normalizados para UTC. Sem `valid_until_utc`, frescor é `UNAVAILABLE`.

## Envelope v1

O serviço de apresentação deverá retornar um objeto JSON com este formato lógico:

```json
{
  "schema_version": 1,
  "generated_at_utc": "<ISO-8601 UTC>",
  "as_of_utc": "<instante da decisão ou consulta>",
  "scope": {
    "symbol": "<símbolo>",
    "timeframe": "<timeframe>",
    "strategy_id": null,
    "run_id": null
  },
  "comparison": {
    "kind": "FIXED_LEDGER_COUNTERFACTUAL",
    "label": "Contrafactual sobre operações existentes; sem reexecução",
    "state_changes_replayed": false
  },
  "evidence": {
    "state": "EXPLORATORY",
    "reason": "<motivo curto>",
    "freshness": "CURRENT"
  },
  "provenance": {
    "sources": [],
    "period_start_utc": "<ISO-8601 UTC>",
    "period_end_utc": "<ISO-8601 UTC>",
    "dataset_hash": "<sha256 ou null>",
    "source_revision": "<revisão ou null>",
    "available_at_utc": "<ISO-8601 UTC ou null>",
    "valid_until_utc": "<ISO-8601 UTC ou null>"
  },
  "original": {},
  "candidate": {},
  "delta": {},
  "signals": {
    "accepted": null,
    "blocked": null,
    "source": "NOT_RECORDED"
  },
  "stability": {
    "state": "INSUFFICIENT",
    "method": null,
    "folds": null,
    "estimate": null,
    "interval": null
  }
}
```

Valores permitidos:

- `comparison.kind`: `OBSERVED_LEDGER`, `FIXED_LEDGER_COUNTERFACTUAL`, `STRATEGY_RESIMULATION` ou `SHADOW_LOG`.
- `evidence.state`: `EXPLORATORY`, `VALIDATED` ou `INSUFFICIENT`. `evidence.freshness` é `CURRENT`, `STALE` ou
  `UNAVAILABLE`; a UI mostra `STALE`/`UNAVAILABLE` mesmo que uma avaliação histórica tenha sido validada.
- Cada métrica contém `value`, `unit` e `state`. Para indisponibilidade, `value` é `null` e `state` explica o motivo,
  por exemplo `NOT_PROVIDED`, `INCOMPLETE_COSTS`, `INSUFFICIENT_SAMPLE`, `INCOMPLETE_TIME_DATA` ou
  `UNAVAILABLE_TIME_ORDER`.
- O adaptador da branch sempre retorna `FIXED_LEDGER_COUNTERFACTUAL` e `state_changes_replayed: false`; ele não
  declara reexecução da estratégia, publicação de snapshot ou sinais observados.
- `evidence.freshness` é calculado com `as_of_utc` e `valid_until_utc` fornecido pelo chamador. O adaptador não inventa
  validade nem horário de disponibilidade; `provenance.availability_state` permanece `UNAVAILABLE` no estado atual.

## Métricas

`original` e `candidate` devem oferecer os mesmos campos, com unidade declarada:

- `n_operations`, `sample_adequacy`;
- `recorded_pnl_total`, `recorded_pnl_mean_per_operation`, `recorded_pnl_median_per_operation`;
- `net_pnl_total`, `net_pnl_mean_per_operation` e `net_pnl_median_per_operation`;
- `recorded_pnl_max_drawdown_amount` e `recorded_pnl_max_drawdown_pct`;
- `max_drawdown_amount` e `max_drawdown_pct` para o PnL líquido;
- `peak_exposure` em volume bruto simultâneo da fonte para um único símbolo;
- `costs`, com componentes `spread`, `commission`, `slippage`, `swap` e `fees`, cobertura e componentes ausentes.

As colunas opcionais são `cost_spread`, `cost_commission`, `cost_slippage`, `cost_swap` e `cost_fees`. O payload
retorna cobertura por componente em `costs.coverage_by_component` (fração de operações com valor finito). Cada custo
deve ser um valor numérico finito não nulo, com sinal conforme a convenção de custos/rebates da fonte, na mesma unidade de
`pnl`. Com `pnl_basis="gross"`, o adaptador subtrai a soma dos cinco custos por operação. Com `pnl_basis="net"`, trata
`pnl` como líquido já calculado; em ambos os casos, os cinco componentes precisam estar completos para exibir
`net_pnl_*`. Com o padrão `pnl_basis="unknown"`, os campos líquidos são nulos. Resultado registrado é mostrado
separadamente como `recorded_pnl_*`, sem inferência sobre base bruta ou líquida.

Drawdown segue `exit_time` em ordem cronológica. Sem horário completo e ordenável, seus campos ficam indisponíveis.
O valor percentual só é calculado quando `initial_equity` positivo é informado; sem ele, somente o valor absoluto pode
ser exibido. Exposição exige `entry_time`, `exit_time`, `volume` e exatamente um `symbol`; mede soma dos volumes
absolutos simultaneamente abertos e não converte unidade do ativo.

`delta` contém candidato menos original apenas quando a métrica está disponível nos dois lados. `sample_adequacy` usa
`minimum_operations` (padrão 30) como limite de triagem. Essa regra não valida uma hipótese: o estado geral permanece
`EXPLORATORY` ou `INSUFFICIENT`.

`signals.accepted` e `signals.blocked` são `null` com `source: "NOT_RECORDED"` quando não existe log de sinais. Não
se infere zero a partir de um ledger de operações. Contagens só são preenchidas para uma fonte que registra também
sinais bloqueados, como o futuro modo sombra T13.7a.

`stability` informa método, partições temporais, estimativa e intervalo. A UI não deve converter intervalo ou
significância em probabilidade de lucro. Sem evidência temporal suficiente, `state` é `INSUFFICIENT` e os limites
ficam nulos.

No adaptador atual, `stability.estimate` é somente a fração de partições walk-forward cujo expectancy após filtro
supera a expectancy antes do filtro, entre partições comparáveis retornadas por `rules.evaluate`. `interval` fica
sempre nulo; não é probabilidade nem teste estatístico.

`build_hypothesis_catalog` preserva todas as tentativas que o leitor T13.4 retorna para os filtros. Cada hipótese tem
`lifecycle_status`; cada tentativa tem seu próprio `status` e `evidence_state`. Uma avaliação aprovada só aparece como
`VALIDATED` quando a linha persistida está `APPROVED`, seu resultado registra `eligible_for_approval: true` e a reserva
OOS não foi reutilizada. Datas de validade, revisão da fonte e período da fonte ainda não existem no esquema T13.4;
nesses casos, frescor é `UNAVAILABLE` e a proveniência lista os campos ausentes.
